## 1. Goals and non-goals

**Goals**

1. A teacher can create a test in minutes, on a laptop or a phone. Alternatively, they can import a JSON file, written by hand or generated by a local or cloud LLM.
2. Students take the test on their own phones over the host's local network. They need no internet, no app install and no account.
3. Answers are graded automatically by per-question rules. Open answers go to a quick manual review queue.
4. Results print as lean PDF **sheets**, each holding the taker's info, the question/answer sequence and the score.
5. Teachers keep a light record of students and groups, with their results over time.
6. An optional local LLM helps with tedious work such as importing class lists or structuring a test. The app never requires it.
7. The app runs well on a modest laptop and on low-end phones over weak Wi-Fi.
8. The UI ships in English first and Ukrainian next, and is built to accept more languages.

**Non-goals for v1**

- Proctoring or anti-cheating: no lockdown browser and no camera.
- Cloud or multi-school hosting. One host is one installation, and nothing is exposed to the internet.
- LMS features such as courses, assignment calendars or messaging.
- Native mobile apps. The app is mobile web only.
- Real-time co-editing of the same test.

## 2. Users and roles

| Role | Who | Can |
|---|---|---|
| **Admin** | Whoever installs and runs the host, often also a teacher | Manage teacher accounts, system settings (network, LLM, school name) and backups, plus everything a teacher can do |
| **Teacher** | A logged-in user | Manage their own projects and tests, open sessions, view results, grade, print, manage their own students and groups, import and export |
| **Taker** (guest) | Anyone with a session link | Take a test and see the result if the test allows it. Needs no account |
| **Student** | A roster entry owned by a teacher | Has no login in v1. Attempts are linked to this record. An optional student login is planned in KT-608 |

## 3. Glossary

Implementers should use these names consistently. Where the code name differs from the UI term, it's to avoid a clash.

| UI term | Code name | Meaning |
|---|---|---|
| Project | `Project` | A folder of related tests, for example "Algebra, 7th grade" |
| Test | `Assessment` | An authored set of questions and settings. The code name avoids clashing with pytest/unittest `Test*` class collection |
| Question / Option | `Question` / `Option` | |
| Revision | `Revision` | An immutable snapshot of a test, created on publish and stored as a Test Document (JSON). Sessions and attempts always point to a revision, so editing a test never changes past results |
| Session | `Sitting` | One opening of a test for takers, with its own short code, link, QR, time window and optional group. The code name avoids confusion with Django's sessions |
| Attempt | `Attempt` | One taker's pass through a session |
| Answer | `Answer` | The response to one question within an attempt, with its score |
| Sheet | none (rendered view) | The printable view of an attempt: taker info, question/answer sequence, score and grade |
| Group | `StudentGroup` | A class or cohort. The code name avoids clashing with `django.contrib.auth.models.Group` |
| Student | `Student` | A roster entry |
| Test Document | `exchange.TestDocument` | The canonical JSON format of a test, used for import, export and revision snapshots |
| Grade scale | `GradeScale` (value object) | The rule that maps a percentage to a mark |

## 4. Key user flows

**4.1 Prepare a test.** The teacher logs in and opens Projects, then New test. They fill in settings and add questions. Alternatively they choose *Import JSON*, review the validation report and preview, and create the test. They then *Preview as taker* and *Publish*, which creates Revision 1.

**4.2 Run it in class.** The teacher chooses *Open session*, picking the test and optionally a group and a time window. The share screen shows a big QR code, a short URL and a session code for projecting onto the board. Students scan the code with their phone camera, enter their name (or pick it from the class list), answer and submit. The teacher watches a live counter, then chooses *Close session*. Any attempts still in progress are submitted automatically with their saved answers.

**4.3 Review, grade and print.** On the session results page, automatic scores are ready immediately. The review queue presents open answers one at a time for a score and a comment. *Print* produces a single sheet or the whole session as one PDF. Optionally, the teacher links the results to student profiles.

**4.4 Create a test with an LLM.** The teacher pastes the prompt pack (`docs/llm/`) and their material into any LLM and gets JSON back. They import it. If validation fails, the error report is worded so it can be pasted back to the LLM for a fix, then imported again. With the local LLM enabled, the teacher pastes material into *Draft test with assistant* instead. The job runs, a preview appears, and the result is imported as a draft.

## 5. Architecture

### 5.1 Deployment model

```
 ┌────────────────────────── Host (teacher laptop, Windows 10/11) ─────────────────────────┐
 │  Waitress WSGI  0.0.0.0:8000  ──  Django app  ──  SQLite (WAL) + media/  (data folder)    │
 │                                        │                                                 │
 │                                        └── optional: Ollama / any OpenAI-compatible LLM  │
 │                                            at 127.0.0.1:11434, or on another LAN machine │
 └──────────────────────────────────────────┬──────────────────────────────────────────────┘
                                            │  Wi-Fi / LAN (no internet required)
          ┌─────────────────────────────────┼─────────────────────────────────┐
   Student phones                     Teacher phone/tablet              Projector
   http://192.168.1.23:8000/s/K7QX2M   http://192.168.1.23:8000/teach/   share screen with QR
```

### 5.2 Principles

- **Offline by construction.** The app uses no CDNs, no web fonts and makes no calls to external services. Everything is vendored, and a test enforces it (KT-008). A CSP header of `default-src 'self'` backs this up.
- **Server-rendered HTML first.** HTMX enhances the pages, but the taker flow works with JavaScript disabled.
- **One canonical test format.** The Test Document (§11) serves as the import format, the export format, the published revision snapshot and the grading input.
- **Grading is pure functions.** Scoring takes a `(TestDocument, answers)` pair and returns scores. It's deterministic, unit-testable and safe to re-run (regrading).
- **Optional features degrade cleanly.** With the LLM off or unreachable, assistant actions are hidden and nothing breaks.
- **One process, one database file, one data folder.** A backup is a copy of the folder.

### 5.3 Network budget for a taker

Entering a session takes 1 GET and 1 POST. A single-page test takes 1 GET, some tiny autosave POSTs and 1 submit POST. No other assets are fetched after the first visit, because static files are cached with far-future headers.

## 6. Tech stack

**Recommendation: Django (server-rendered) with HTMX, SQLite and Waitress.** The stack is pure Python with no Node build step.

Django suits this app because it already ships what the app mostly consists of: auth and permissions, an admin, forms and validation, an ORM with migrations, i18n (gettext, including Ukrainian plural forms), CSRF protection, file uploads and management commands. Python also has the strongest ecosystem for local LLMs and document processing, both needed in Phase 7.

### 6.1 Platform

| Layer | Choice | Why |
|---|---|---|
| Language | **Python 3.13** (3.12 or later) | Required by Django 6. Best tooling for LLMs and documents |
| Environment and packages | **uv** (`pyproject.toml` + `uv.lock`) | Fast and reproducible. Installs Python itself on Windows |
| Web framework | **Django 6.x**: the latest stable release at Phase 0, moving to 6.2 LTS when it ships (expected April 2027) | Batteries included. The built-in template partials pair well with HTMX, and the built-in CSP middleware enforces the no-external-requests rule |
| Database | **SQLite 3 in WAL mode** | Zero configuration and a single file. Easily handles one classroom (40–60 concurrent takers, small writes). Backup is a file copy |
| App server | **Waitress** | A pure-Python, threaded, production WSGI server that runs on Windows (Gunicorn does not) |
| Static files | **WhiteNoise** | Serves compressed, cache-busted static files straight from Django, so no nginx is needed |
| Interactivity | **HTMX 2** (vendored) plus small vanilla JS modules | Partial page updates without an SPA, at about 16 KB gzipped |
| CSS | **Hand-written CSS** with custom-property tokens, no framework and no build step | Small (target under 15 KB) and fully controlled, which avoids the generic template look |
| PDF | **fpdf2** | Pure Python and Windows-friendly (WeasyPrint needs GTK/Pango). Embeds Unicode TTF fonts with subsetting, which keeps files small |
| QR codes | **segno** | Pure Python. SVG output stays crisp on projectors, and it can also print a QR code in the terminal |
| Schema and validation | **pydantic v2** | One definition provides validation, JSON Schema generation and LLM output checking |
| LLM | Any **OpenAI-compatible** server, Ollama by default, called with **httpx** | Swapping engines needs no code changes |

### 6.3 Deliberately not used

| Not used | Reason |
|---|---|
| Node/npm, bundlers, Tailwind, React/Vue | They add a build step and heavier client payloads, which server-rendered forms don't need |
| PostgreSQL/MySQL | Another service to install and run. SQLite is enough for a single host, and Django makes a later switch easy |
| Celery/Redis | There's no heavy background work. LLM jobs use an in-process worker (§15.2) |
| nginx/Docker | Not needed for a LAN app on Windows. Docker may be added later for Linux hosts |
| WeasyPrint | Excellent output, but it needs GTK/Pango on Windows |
| Web fonts and icon fonts | They cost bytes on weak Wi-Fi, and system fonts look native anyway |

### 6.4 Alternatives considered

| Option | Verdict |
|---|---|
| Flask/FastAPI with Jinja | A lighter core, but auth, admin, forms, migrations and i18n would all be hand-built, and they make up most of this app |
| Node (Next.js/SvelteKit) | Brings build tooling and heavier client JS. A weaker fit for low-end phones and for offline packaging on Windows |
| PocketBase (Go single binary) | Great distribution story, but the UI becomes a separate SPA, and the i18n, PDF and LLM tooling is weaker. Revisit only if a single `.exe` becomes the top priority |
| Existing open-source tools (LimeSurvey, Moodle quiz) | Heavy (PHP plus a database server), complex to run on one teacher's laptop, not lean on mobile, and without an LLM-friendly schema |

## 9. Question types and scoring rules

### 9.1 Types in v1

The concept names four kinds of task. The table maps them to v1 types. This mapping is an assumption awaiting confirmation (Q1 in §23).

| Concept term | Type | Control | Description |
|---|---|---|---|
| single-correct | `single_choice` | Radio buttons | Exactly one correct option |
| few-correct | `choose_n` | Checkboxes, at most *n* selectable | "Pick exactly *n*", for example 3 of 7 as in the Ukrainian NMT tests. Exactly *n* options are correct |
| multiple-choice | `multiple_choice` | Checkboxes | Any number of correct options (one or more). The scoring mode is configurable |
| open-question | `short_answer` | Single-line input | Autograded against accepted answers, as text or as a number |
| open-question | `open` | Textarea | Graded manually, with an optional rubric |

Later types stay in the backlog and are not in v1: `true_false` (a preset of `single_choice`), `matching`, `ordering`, and ungraded `rating`/survey questions. Numeric answers are covered by `short_answer` in numeric mode.

### 9.2 Rules

Notation: **P** = the question's points, **C** = the correct options, **I** = the incorrect options, **S** = the options the taker selected, **R** = S ∩ C (correct picks), **W** = S ∩ I (wrong picks).

| Type | Rule |
|---|---|
| `single_choice` | P if S = {the correct option}, otherwise 0. Optional `penalty` (0–1): a wrong answer (not a blank one) scores −penalty·P |
| `multiple_choice`, `partial` (default) | P · max(0, \|R\|/\|C\| − \|W\|/\|I\|). Selecting every option scores 0, so guessing everything doesn't pay |
| `multiple_choice`, `all_or_nothing` | P if S = C, otherwise 0 |
| `multiple_choice`, `per_option` | The sum of the teacher-set `weight` of each selected option, clamped to [0, P] |
| `choose_n` | P · \|R\| / n. The UI caps selections at n, so wrong picks cost a correct slot |
| `short_answer`, `text` mode | P if the normalized answer equals any normalized `accept` entry, otherwise 0. With `review_unmatched`, a non-matching answer goes to review instead of scoring 0 (useful for typos) |
| `short_answer`, `numeric` mode | P if \|answer − accepted\| ≤ `tolerance` for any accepted value. Both "," and "." are accepted as decimal separators |
| `open` | Status `needs_review` until the teacher sets a score from 0 to P in steps of 0.5. The LLM can suggest a score (Phase 7); the teacher always confirms |

**Worked example** for `multiple_choice` in `partial` mode, with P = 2, C = {a, b} and I = {c, d}:

| Selected | \|R\|/\|C\| − \|W\|/\|I\| | Score |
|---|---|---|
| a, b | 1 − 0 | 2.0 |
| a | 0.5 − 0 | 1.0 |
| a, b, c | 1 − 0.5 | 1.0 |
| a, c | 0.5 − 0.5 | 0 |
| a, b, c, d | 1 − 1 | 0 |

**Common rules**

- A blank answer always scores 0. A single question can only score below 0 when it's a `single_choice` with a `penalty` set. An attempt's total never goes below 0.
- `points: 0` marks a question as ungraded (for example a survey question). It's excluded from the maximum score.
- If grading is disabled for a test, nothing is scored and the test behaves like a plain form.
- Scores are Decimal values rounded to 2 places. Percent = earned ÷ maximum graded points × 100, rounded to 1 place.
- While any answer is `needs_review`, the attempt total and grade are shown as **provisional**.
- `required` questions block submission while unanswered. A timed-out auto-submit ignores this.

### 9.3 Text normalization (short answers)

Normalization runs in this order:

1. Unicode NFKC.
2. Trim and collapse whitespace.
3. Casefold, unless `case_sensitive` is set.
4. Unify apostrophes (`'` `’` `ʼ` and backtick become one character), which matters for Ukrainian words such as "м'ята".
5. Unify dashes and quotes.
6. Strip trailing punctuation.

An optional per-question flag also maps Latin look-alike letters to Cyrillic (for example Latin `i` to Cyrillic `і`), to catch keyboard-layout slips.

## 10. Grade scales

The grade is derived from the attempt's percentage through a threshold table ("percent ≥ min_percent gives this label"), evaluated from the top down. Presets are editable copies, not hard-coded rules.

| Preset | Output |
|---|---|
| `percent` (default) | "83.3 %" |
| `points` | "7.5 / 9" |
| `pass_fail` | "Pass" or "Fail" at `pass_percent` (default 50) |
| `ua_12` | Marks 1–12 in twelve equal percent bands. **Not an official standard**; teachers should adjust the bands to their school's policy |
| `five_point` | Marks 2–5 with editable thresholds |
| `custom` | The test's own `thresholds` list: `[{min_percent, label}, …]` |

Teachers can save their own scales and reuse them across tests. That's a Should item in KT-403.

## 11. Exchange format (JSON)

### 11.1 Design rules for LLM-friendliness

- **One file, one test.** The top-level `format` and `version` fields identify the document.
- **Flat and explicit.** Correctness is marked inline on options (`"correct": true`), with no cross-references by index.
- **Optional ids.** Ids (`q1`, `a`) may be left out on import and are generated automatically. Exports always include them.
- **Defaults for everything optional.** The smallest valid file is a few lines long.
- **Small, lowercase snake_case enums** and plain text. Line breaks are kept. Markdown and formulas are deferred.
- **Lenient import, strict export.** Unknown fields produce a warning and are ignored. Exports are always canonical.
- **Fixable errors.** Every error names its location and says what to change in plain words, so an LLM (or a person) can fix it in one pass.

### 11.2 Test Document v1 (full example)

```json
{
  "format": "knowledge-tester/test",
  "version": 1,
  "test": {
    "title": "Fractions: basics",
    "description": "Quick check after lesson 4.",
    "language": "en",
    "settings": {
      "time_limit_minutes": 15,
      "shuffle_questions": false,
      "shuffle_options": true,
      "one_question_per_page": false,
      "show_result": "score",
      "max_attempts": 1
    },
```

### 11.3 Field reference

**Test level**

| Field | Values | Default |
|---|---|---|
| `format` | `"knowledge-tester/test"` | required |
| `version` | `1` | required |
| `test.title` | string, 1–200 characters | required |
| `test.description` | string | `""` |
| `test.language` | BCP-47 code: `en`, `uk`, … | `"en"` |
| `settings.time_limit_minutes` | integer ≥ 1, or `null` | `null` (no limit) |
| `settings.shuffle_questions` / `shuffle_options` | bool | `false` |
| `settings.one_question_per_page` | bool | `false` |
| `settings.show_result` | `none` · `score` · `full` (score plus correct answers) | `score` |
| `settings.max_attempts` | integer ≥ 1 | `1` |
| `taker_fields` | `[{key, label, required}]` | `[{"key":"name","label":"Full name","required":true}]` |
| `grading.enabled` | bool | `true` |
| `grading.scale` | `percent` · `points` · `pass_fail` · `ua_12` · `five_point` · `custom` | `percent` |
| `grading.pass_percent` | number, 0–100 | `50` |
| `grading.thresholds` | `[{min_percent, label}]`, used only with `custom` | none |
| `questions` | 1–200 items | required |

**Question level**

| Field | Applies to | Values | Default |
|---|---|---|---|
| `id` | all | string, unique within the test | generated: `q1`, `q2`, … |
| `type` | all | `single_choice` · `multiple_choice` · `choose_n` · `short_answer` · `open` | required |
| `text` | all | string, 1–5000 characters, plain text | required |
| `points` | all | number ≥ 0, in steps of 0.5. `0` means ungraded | `1` |
| `required` | all | bool | `false` |
| `hint` | all | string, shown under the question | none |
| `options` | choice types | 2–20 items of `{id?, text, correct?, weight?}` | required |
| `scoring` | `multiple_choice` | `partial` · `all_or_nothing` · `per_option` | `partial` |
| `penalty` | `single_choice` | number from 0 to 1 | `0` |
| `n` | `choose_n` | integer ≥ 1, and must equal the number of correct options | required |
| `mode` | `short_answer` | `text` · `numeric` | `text` |
| `accept` | `short_answer` | non-empty array of strings. In numeric mode they hold numbers | required |
| `case_sensitive` | `short_answer` (text) | bool | `false` |
| `tolerance` | `short_answer` (numeric) | absolute value ≥ 0 | `0` |
| `review_unmatched` | `short_answer` | bool | `false` |
| `rubric` | `open` | string, shown to the reviewer (and to the LLM) | none |
| `image` | all | path inside a bundle. Reserved in plain JSON v1 | none |

**Semantic checks**, which run after the schema is validated:

- A `single_choice` question has exactly one correct option.
- A `multiple_choice` question has at least one correct option.
- A `choose_n` question has exactly `n` correct options.
- Option and question ids are unique.
- With `per_option` scoring, every option has a weight.
- `custom` scales have thresholds sorted with unique labels.

### 11.4 Validation report

Import never fails silently. Errors block the import, warnings don't. Every message carries a path and a plain instruction:

```
ERROR  questions[1] (id "q2", multiple_choice): no option is marked correct. Add "correct": true to at least one option.
ERROR  questions[3].points: must be 0 or more, got -1.
WARN   test.settings.shuffle: unknown field, ignored. Did you mean "shuffle_options"?
```

The same report can be downloaded as text so it can be pasted back to an LLM.

### 11.5 Related formats

**Results** (`knowledge-tester/results`, v1): the export of a session.

```json
{
  "format": "knowledge-tester/results",
  "version": 1,
  "exported_at": "2026-11-10T10:15:00Z",
  "session": { "code": "K7QX2M", "title": "7-A, lesson 5", "opened_at": "…", "closed_at": "…" },
  "test": { "…": "the revision's full test object, exactly as in the Test Document" },
  "attempts": [
    {
      "taker": { "name": "Ivan Petrenko", "class": "7-A" },
      "status": "submitted",
      "started_at": "…",
      "submitted_at": "…",
      "score": 7, "max_score": 9, "percent": 77.8, "grade": "10",
      "answers": [
        { "question_id": "q1", "value": ["a"], "points": 1, "status": "graded" },
```

In `value`, choice types hold an array of option ids. `short_answer` and `open` hold a string.

**Bundle** (`knowledge-tester/bundle`, v1): a whole project as `{ format, version, project: {title, description}, tests: [<test objects>] }`. When tests contain images, the bundle is a `.zip` holding `bundle.json` and a `media/` folder.

### 11.6 Versioning policy

`version` is an integer. Adding optional fields doesn't bump it. A breaking change bumps it, and the importer keeps upgrading older versions so old files always import.

## 12. Delivery on the LAN

### 12.1 Sessions

- A teacher opens a session from a published test, which pins the current revision. Options:
  - a title (for example "7-A, Monday")
  - an optional group (§14)
  - an optional closing time or duration
  - an optional access code
  - overrides for the time limit and `show_result`
- **Session code:** 6 characters from an unambiguous alphabet (`23456789ABCDEFGHJKMNPQRSTUVWXYZ`, which drops 0/O, 1/I/L). That gives about 8.9 × 10⁸ combinations, which is enough on a LAN. Codes are case-insensitive.
- Lifecycle: open → closed. A test can have any number of sessions, and results are kept per session.
- **Closing** finalizes every in-progress attempt using its autosaved answers (status `auto_submitted`).

### 12.2 Links and QR codes

- The taker URL is `http://<host-ip>:<port>/s/<CODE>`. On the landing page, takers can also type the code, as a fallback when scanning fails.
- **IP selection:** private IPv4 ranges are preferred. Loopback, link-local (169.254.x) and virtual adapters (Hyper-V `vEthernet`, WSL, VirtualBox, VMware, Docker) are skipped. The teacher can switch interfaces on the share screen, and the choice is remembered.
- The **share screen** (presentation mode) shows:
  - a QR code as SVG, about 60% of the viewport
  - the URL in large monospace
  - the session code
  - live counters (joined / in progress / submitted), polled every 5 seconds

### 12.3 Taker experience

1. **Session page:** the title, description, question count, time limit, identity fields (or a pick-your-name list for group-bound sessions), the access code if set, and **Start**.
2. **Questions:** the default is one scrollable page, which minimizes requests on flaky networks. An optional mode shows one question per page. A sticky bottom bar shows the answered count, the timer and the next or submit action.
3. **Review:** unanswered questions are listed with jump links, then the taker confirms and submits.
4. **Done:** depending on `show_result`, the page shows "Submitted", the score, or the score with correct answers.

Mobile rules for these pages are in §17.4. The whole flow works without JavaScript as plain form posts.

### 12.4 Resilience

- **Attempt token cookie**, one per session. Reopening the link resumes the attempt.
- **Autosave:** HTMX posts each change, debounced, to the server. A localStorage mirror covers dropped connections, and pending saves are retried on reconnect.
- **Idempotent submit:** a repeated submit POST just returns the done page.
- **Timer:** the server's deadline is authoritative and the client only displays a countdown. When time runs out, the client auto-submits. If the client is gone, the server finalizes the attempt on the next request or when the session closes. The teacher can extend time per attempt.
- **Shuffling:** the question and option order is generated once per attempt (seeded) and stored, so review and PDF show what the taker saw.

### 12.5 Attempt limits and identity (soft)

`max_attempts` is enforced per browser (cookie) and per normalized name within a session. Guests can get around this by clearing cookies, so the limit is a convenience, not security. Suspected duplicates are flagged on the results page. For stricter identity, use group-bound sessions with PINs (§14).

### 12.6 Teacher live monitor

A table of takers shows status, answered count against total, and time left. Actions: extend time, void attempt and close session. It updates by HTMX polling.

## 13. Results, review and printing

### 13.1 Results views

- **Session summary:** number of takers, average, median, score distribution (simple bars rendered on the server), and the number of reviews pending.
- **Attempts table:** sortable by name, score or time, with filters for status and needs-review.
- **Attempt detail:** the on-screen sheet.
- **Item analysis:** percent correct per question, and the most-chosen wrong options.

### 13.2 Review queue

Answers that need review (`open`, or `short_answer` with `review_unmatched`) are presented one at a time: the question, rubric, answer, a points input and a comment, then save and next. It's usable one-handed on a phone. Ordering by question (grade question 5 for everyone, then question 6) is the default, because it's faster and fairer.

### 13.3 PDF sheet

```
┌──────────────────────────────────────────────────────────────┐
│ Lyceum No. 5                                 10.11.2026 09:40 │
│ Fractions: basics (rev. 3) · Session: 7-A, lesson 5           │
│ Full name: Ivan Petrenko      Class: 7-A                      │
│ Score: 7 / 9 (77.8 %)   Grade: 10                             │
├──────────────────────────────────────────────────────────────┤
│ 1. Which fraction equals 0.5?                     1 / 1  OK   │
│    Answer: 1/2                                                │
│ 2. Select every fraction greater than 1/2.        1 / 2  PART │
│    Answer: 3/4    Correct: 3/4; 2/3                           │
│ 5. Explain how to compare two fractions…          2 / 3       │
│    Answer: First I bring both to a common denominator…        │
│    Comment: Add an example.                                   │
├──────────────────────────────────────────────────────────────┤

└──────────────────────────────────────────────────────────────┘
```

- **Layout:** A4 portrait (Letter optional), 12 mm margins, 9.5–10 pt type, a bundled Unicode TTF (Latin and Cyrillic) embedded as a subset.
- **Modes:**
  - **compact** (the default): only the chosen answers.
  - **full:** every option, with the chosen and correct ones marked.
- **Options:** include correct answers, include teacher comments, include unanswered questions, truncate long question text, and paper size.
- **Result markers:** text (OK / PART / NO / PENDING) or glyphs that the bundled font is verified to contain. A provisional total is labelled as such.
- **Batch:** a whole session or a selection becomes one PDF, sorted by name, with each sheet starting a new page. A "continuous" option saves paper.
- **Size targets:** a sheet of about 20 questions is 50 KB or less. A batch of 40 sheets is 1 MB or less, because fonts are embedded once.
- **File names:** slugified with Unicode allowed, for example `fractions-basics_7-a_ivan-petrenko.pdf`.
- **Browser printing:** the on-screen sheet view also has a print stylesheet, so plain browser printing works with no PDF step.

### 13.4 Other exports

- **CSV:** one row per attempt, with taker fields, score, percent, grade and points per question.
- **XLSX:** the same, as the `openpyxl` extra.
- **Results JSON:** see §11.5.

## 14. People: teachers, students, groups

- **Teacher accounts** are created by an admin in `/manage/`. Optional self-registration with an invite code is off by default. Password resets are done by the admin, since there's no email on a LAN.
- **Ownership:** teachers see only their own projects, groups, students and sessions. Admins see everything. Sharing projects between teachers is a Could item (KT-607).
- **Groups and students:** created by hand, by pasting a list (one name per line, optionally `Name; Group`), by CSV/XLSX import, or with the LLM import (§15). Every route ends in the same **preview and confirm** screen with duplicate detection.
- **Group-bound sessions:** the taker picks their name from a searchable class list, optionally confirmed with a PIN, and the attempt is linked to the student automatically.
- **Free-name sessions:** afterwards, a *Link to students* screen suggests matches (normalized and fuzzy, via `difflib`) for the teacher to confirm. This is how the teacher "saves results for some students".
- **Student profile:** all linked attempts (test, date, score, grade), averages per project, teacher notes, and a CSV or PDF summary.
- **Group gradebook:** a matrix of students by sessions, exportable to CSV.
- **Deletion:** deleting a student either unlinks their attempts or deletes them, at the teacher's choice. Personal data can be removed (§18).

## 15. Local LLM assistant

### 15.1 Principles

1. **Optional.** The app is fully usable without an LLM. Assistant actions are hidden when it's disabled or unreachable.
2. **Assistive.** LLM output is always a *proposal* shown in a preview. Nothing is saved, published or graded without the teacher confirming it.
3. **Local by default.** The default endpoint is localhost. If the endpoint isn't local or on the LAN, a privacy warning appears, because student data would leave the network.
4. **Structured.** Each feature has a pydantic output schema. The app asks for JSON-schema-constrained output when the server supports it (Ollama does) and always validates the result. If validation fails, it retries up to 2 times with the validation errors added to the prompt. After that, it shows the raw output with the errors.
5. **Bounded.** Inputs are truncated or chunked to fit the model's context. There are timeouts, and only one job runs at a time, which suits a low-end host.

### 15.2 Integration

- **Client:** `assistant.client` is a minimal OpenAI-compatible chat client (`/v1/chat/completions`) over httpx. It handles text and image parts. The health check calls `/v1/models`. It works with Ollama, LM Studio, the llama.cpp server and vLLM.
- **Settings** (in `/manage/`):
  - base URL, default `http://127.0.0.1:11434/v1`
  - text model
  - optional vision model
  - timeout
  - maximum input characters
  - an enabled switch
- **Jobs:** each job is an `LLMJob` row handled by a single in-process worker thread. The page polls the job status through HTMX every 2 seconds and renders the result into a preview. Jobs left running at startup are marked failed. If background work grows, move to Django's tasks framework ([ADR-0006](decisions/0006-llm-openai-compatible-optional.md)).
- **Prompts** are versioned files in `apps/assistant/prompts/`, one per feature, with the output language as a parameter.

### 15.3 Features

| Feature | Input | Output | Task |
|---|---|---|---|
| Import students from text | A pasted, messy list | `[{full_name, group?}]` | KT-703 |
| Import students from an image | A photo or scan of a class list | The same, through a vision model | KT-704 |
| Import students from a file | txt, csv, xlsx, docx or pdf; text is extracted locally first | The same | KT-705 |
| Draft a test from material | Lesson text or notes, plus the desired number and types of questions | Test Document | KT-706 |
| Structure pasted questions | A messy list of questions with answers | Test Document | KT-706 |
| Fix an invalid import | Invalid JSON plus its validation report | A corrected Test Document | KT-706 |
| Editor helpers | One question | Rephrasings, distractor suggestions, an answer-key sanity check | KT-707 |
| Open-answer grading hint | Question, rubric and answer | `{suggested_points, rationale}` | KT-708 |

Non-LLM routes always exist for the same jobs: one name per line, CSV/XLSX import and JSON import.

### 15.4 Model guidance

The model needs good Ukrainian and English, reliable JSON output, vision for image import, and must fit the host's hardware. At planning time, small multilingual instruct models of about 3–8B parameters fit hosts with 8–16 GB of RAM. Examples are Gemma 3 4B, which can also read images, and the small models of the Qwen family. Models change quickly, so re-evaluate when Phase 7 starts using the evaluation fixtures (KT-709). Ollama can also run on another LAN machine with a GPU; point the base URL there.

### 15.5 Safety

Imported content is untrusted. It goes into prompts clearly delimited as data. LLM output is never executed; it's only parsed into validated structures. Images are downscaled to at most 1536 px and stripped of EXIF metadata before they're sent.

## 16. Localization

- **Django i18n from day one.** Every UI string is wrapped (`{% translate %}`, `gettext_lazy`). The settings use `LocaleMiddleware` and `LANGUAGES = [("en", "English"), ("uk", "Українська")]`. Note that the code for Ukrainian is `uk`, not `ua`.
- **Rollout.** Phases 0–7 ship English only. The `uk` catalog is created empty in Phase 0 so the tooling works from the start. The full translation lands in Phase 8.
- **Language resolution:**
  - Teacher UI: user preference, then the browser language.
  - Taker pages: the test's content `language`, so a Ukrainian test shows Ukrainian buttons, then the browser language.
- **Content versus UI.** The app doesn't translate test content. A test's `language` field controls the taker interface language and the PDF labels.
- **Plurals.** Ukrainian has three plural forms, so counts always go through `ngettext` or `{% blocktranslate count %}`.
- **Formats.** Ukrainian display uses `dd.mm.yyyy` dates and decimal commas. Input parsing accepts both separators.
- **Grading normalization** for Ukrainian is covered in §9.3.
- **Fonts.** System fonts render Cyrillic on every target device. The bundled PDF font must cover Cyrillic, which fixtures verify.
- **Tooling.** GNU gettext is required on Windows for `makemessages`. Compiled `.mo` files are committed. `django-rosetta` (optional) edits translations in the browser.
- **Adding a language later** means adding it to `LANGUAGES` and adding a `.po` file.

## 17. UI/UX guidelines

### 17.1 Principles

Practical before decorative. Content comes first. Each screen has one obvious primary action. Layouts start from a 360 px-wide phone, and pages must stay fast on poor Wi-Fi.

### 17.2 Avoid (the generic AI-generated look)

- Cards with a colored **left border** or stripe as an accent.
- Purple, indigo or violet **gradients**, gradient text and neon glows.
- Glassmorphism, backdrop blur and heavy drop shadows.
- Emoji or "sparkle" icons in headings, buttons or empty states.
- Pill badges and icons in colored circles on every item.
- Hero headers and marketing-style stat tiles on dashboards.
- Cards nested in cards, border radii above 8 px, and so much whitespace that content falls below the fold on a phone.
- Decorative icons beside every label, and skeleton shimmer loaders.

### 17.3 Visual system

- **Fonts:** the system stack, `system-ui, -apple-system, "Segoe UI", Roboto, "Noto Sans", sans-serif`. It looks native and costs zero bytes.
- **Palette:** a neutral base (near-black text on white or off-white, gray hairline borders) plus **one** restrained accent color for primary actions, links and focus. Semantic colors (green, red, amber) appear only for correctness and status, and always with a text label beside them.
- **Hierarchy** comes from type size, weight and spacing. Borders are 1 px with 4–6 px radius.
- **Data** goes in plain lists and tables. Tables reflow into stacked rows on phones.
- **Controls** are native and lightly styled. Buttons carry text labels; icons are used only where they're universally understood.
- **Tokens** are CSS custom properties: `--bg`, `--surface`, `--text`, `--muted`, `--border`, `--accent`, `--accent-contrast`, `--ok`, `--warn`, `--bad`, `--radius`, `--space-1…6` and `--fs-*`. Dark mode comes almost free through `prefers-color-scheme`.

### 17.4 Mobile rules

- Tap targets are at least 44 × 44 px, and the whole option row is the target.
- Inputs use a font size of at least 16 px, which stops iOS from zooming on focus.
- Layouts are a single column below 640 px, with a sticky bottom action bar on taker pages.
- Nothing depends on hover. Avoid fixed-height layouts that break when the on-screen keyboard opens.
- Test at 360 × 640.
- **Teacher area:** a top bar (app or school name; Projects · Sessions · Students · Settings) that collapses into a simple menu on phones. Content is at most about 60 rem wide. The editor is a single column of collapsible question blocks.

### 17.5 Accessibility

- Semantic HTML: `fieldset`/`legend` around option groups and a `label` on every input.
- WCAG AA contrast and visible focus states.
- Respect `prefers-reduced-motion`.
- Color is never the only signal.
- The `lang` attribute follows the test's language.

### 17.6 Performance budget (taker pages)

| Metric | Budget |
|---|---|
| HTML, CSS and JS transferred on first load, excluding images | ≤ 60 KB gzipped |
| JS on taker pages | ≤ 25 KB gzipped, and never required to submit |
| Web fonts | 0 |
| Question images | ≤ 150 KB each after the server resizes them (max 1280 px, WebP/JPEG at quality ~75), lazy-loaded |
| Server response time | p95 under 200 ms with 40 concurrent takers on the host |
| Database queries per taker page | ≤ 10, asserted in tests |
| Browser support | Android Chrome and iOS Safari from about the last 5 years. ES2017-level JS, no build step |

## 18. Security and privacy

- **Teacher and admin pages** require a login. Every query checks object ownership, so teacher A can never load teacher B's data.
- **Taker pages** are reachable only through the session code, plus the optional access code. A closed session accepts no new entries.
- **CSRF protection** covers every form, including taker forms. Session cookies are HttpOnly with SameSite=Lax.
- **Plain HTTP on the LAN** is accepted for a classroom network and documented. As a result, the app never depends on browser APIs that require a secure context (the Clipboard API, Service Workers, `crypto.subtle`) and uses fallbacks such as select-to-copy.
- **ALLOWED_HOSTS** is computed at startup from the detected interface IPs plus `localhost` and any configured names. `KT_ALLOWED_HOSTS` overrides it.
- **Throttling:** a simple cache-based limit on login attempts and on submissions per attempt.
- **Uploads:**
  - Images only, re-encoded by Pillow (which strips metadata and payloads), with a size limit.
  - JSON imports are size-limited (2 MB) and parsed safely.
- **CSP** is `default-src 'self'`, using Django's built-in middleware.
- **Personal data:** the names and answers of minors stay on the host. The app sends no telemetry and keeps backups local. Students and sessions can be deleted or anonymized. A warning appears if the LLM endpoint isn't local.
- **Secrets:** `SECRET_KEY` is generated on first run into the data folder and never committed. `DEBUG` is off in LAN mode.

### 19.2 Network setups

| Setup | Notes |
|---|---|
| Portable Wi-Fi router with no internet uplink | The most reliable option. Recommended for regular use |
| Phone hotspot (mobile data can be off) | Easy, but many phones cap at about 10 clients, which is too few for a full class |
| Windows Mobile Hotspot on the host | Built in, but limited to 8 devices |
| School Wi-Fi | Often has **client isolation**, which stops devices from reaching each other. Check it with the diagnostics page (KT-903) before class |
| Wired LAN or computer lab | Works, with the same firewall rules |

**Host checklist:**

1. Set the Windows network profile to **Private**.
2. Allow inbound TCP on the port. Run this once as administrator:
   `New-NetFirewallRule -DisplayName "Knowledge Tester" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow -Profile Private`
3. Disable sleep for the duration of the lesson.
4. Keep the laptop on mains power.

### 19.3 Data location: the OneDrive caveat

This repository currently lives under `OneDrive\Desktop`, which is fine for code. **It is not fine for the database.** Sync clients lock and rewrite files mid-write, which can corrupt SQLite and its WAL file. For that reason:

- The data folder defaults to `%LOCALAPPDATA%\KnowledgeTester\`, and startup warns when the data folder sits inside a OneDrive, Dropbox or Google Drive folder.
- The virtual environment should also live outside OneDrive. Set `UV_PROJECT_ENVIRONMENT`, so thousands of package files don't get synced.

### 19.4 Backups

- **Automatic** backups run on startup and whenever a session closes. They use SQLite's online backup API and write `backups/kt-YYYYMMDD-HHMM.sqlite3`, plus a zip of `media/`. The last 20 are kept.
- **Manual:** *Download backup* in `/manage/`, and `manage.py restore` to restore one.
- Bundle and results JSON exports double as human-readable archives.

### 19.5 Host hardware

| Use | Requirement |
|---|---|
| Without an LLM | Any laptop from about the last 8 years with 4 GB of RAM, running Windows 10/11 (Linux and macOS also work) |
| With a local LLM | 16 GB of RAM recommended, 8 GB minimum for 3–4B models. A GPU is optional. Alternatively, run the LLM on another LAN machine |

## 20. Quality

### 20.1 Testing strategy

- **Unit tests**, the bulk:
  - every grading rule and edge case, table-driven
  - grade scales and text normalization
  - exchange validation against valid and invalid fixture files with their expected messages
  - serializer round-trips: DB → document → DB → document must be identical
  - session code generation
- **Integration tests** with the Django test client:
  - the full flow: import → publish → open session → take → submit → grade → PDF bytes
  - permissions: teacher A can't reach teacher B's objects
  - query counts on taker pages
- **Offline guard:** render the key pages and fail if the HTML or the static CSS/JS references any external host.
- **Load test:** `scripts/loadtest.py` simulates N takers (40 by default) through the full flow. Run it on the target laptop before each milestone.
- **Manual device checklist** per milestone: a low-end Android phone with Chrome, an iPhone with Safari, a 360 px viewport, and throttled networking (the DevTools slow-network presets).
- **Browser end-to-end tests** (Playwright) are optional later and not part of the MVP.

### 20.2 Definition of Done (every issue)

1. The acceptance criteria are met. Tests are added or updated, and `uv run pytest` and `uv run ruff check .` pass.
2. New UI strings are wrapped for translation.
3. Pages work at 360 px width and make no external requests.
4. New views check permissions.
5. User-visible changes are reflected in the docs (README, user guide, schema docs).
6. The issue file is updated (status and notes), the item is moved on [BOARD.md](BOARD.md), and [log.md](log.md) has an entry if the change is notable.

## 22. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Wi-Fi client isolation blocks traffic from phones to the host | Students can't open the test | Recommend a dedicated router or hotspot; diagnostics page (KT-903); test before class |
| Windows Firewall or a Public network profile blocks the port | Same | The launcher checks and prints the one-time command; documented in §19.2 |
| The host sleeps or crashes mid-test | Lost progress | Server-side autosave plus localStorage; resume by cookie; WAL durability; the "disable sleep" checklist item |
| The SQLite database sits in a OneDrive-synced folder | A locked or corrupted database | The data folder lives outside OneDrive by default, with a startup warning (§19.3) |
| 30 or more simultaneous submits | Lock errors, slow pages | WAL, `IMMEDIATE` transactions and a busy timeout; short transactions; load test (KT-310) |
| Hotspot device limits (about 10 on phones, 8 on Windows) | Not every student can connect | Use a router for a full class (§19.2) |
| Low-end hardware makes the LLM slow or poor | The assistant is unusable | It's optional, jobs are asynchronous, a remote LAN endpoint is possible, and non-LLM routes always exist |
| LLM-generated tests carry wrong answer keys | Wrong grades | Mandatory preview, the key-check helper, regrading after a fix |
| Missing glyphs in PDFs (Cyrillic, symbols) | Broken sheets | A bundled Unicode font and Ukrainian fixtures in the tests |
| Scope creep ("it's Google Forms") | Never shipping | The MVP cut line, phase exit criteria, a backlog for extras |
| Students share answers between phones | Unfair results | Shuffling and time windows; documented as not a proctoring tool |
| GNU gettext missing on Windows | Translations can't be built | Documented install; compiled `.mo` files committed |
